# ADR 0004: 開発プロセス

## Status

Accepted

## Context

これまでは 1 人が Claude Code を使い、1 つのセッションの中で、このリポジトリを手で開発してきた。
ADR 0001 では、画像比較テストと CI を今は作らないと決めた。
ADR 0003 で、デバイスとバックエンドに Go のプログラムを足すことにした。作業は `mobile/`、`device/`、`backend/` にまたがるようになった。
Claude Code、Codex、Grok という複数のコーディングエージェントで開発したい。3 つともインストールしてあり、どれもユーザーの設定から Matt Pocock のスキルを読む。
Matt Pocock のスキルはアイデアから変更のマージまでの流れを示している。herdr はエージェントをターミナルのペインで動かし、その状態(作業中、入力待ち、承認待ち、完了)を知らせる。
共通のチェックのコマンドが 1 つもないと、エージェントは自分の変更が動くかどうかを判断できない。CI がないと、プルリクエストをチェックするものがない。
この ADR は ADR 0001 のうち CI を作らないと決めた部分を置き換える。画像比較テストは引き続き作らない。

## Decision

### ループ

- Matt Pocock のスキルの流れに従い、`/grill-with-docs`、`/to-spec`、`/to-tickets`、`/implement`(`/tdd` と `/code-review` を含む)、`/pr`、`/retro` の順に進める。
- issue tracker として GitHub Issues を使う。仕様書とチケットは issue にする。チケットは仕様書の sub-issue にし、チケットどうしは GitHub に組み込まれたブロックの機能でつなぐ。
- トリアージのラベルは標準の 5 つを使う。
- `AGENTS.md` に、すべてのエージェント向けの指示を書く。`CLAUDE.md` は `@AGENTS.md` でそれを読み込むだけにする。Codex は `AGENTS.md` を、Claude Code は `CLAUDE.md` を、Grok は両方を読む。
- このリポジトリの ADR の書式を残す。エージェントは `domain-modeling` スキルにある書式ではなく、この書式に従う。

### 役割

- 指揮役は Claude Code のエージェントである。人と話し、仕様書とチケットを書き、herdr のペインで実装役とレビュー役を動かす。ブランチを push し、プルリクエストを作るのは指揮役だけである。指揮役の手順はスキルとして書く。
- 実装役は Claude Code と Grok である。実装役はそれぞれ自分のワークツリーで 1 つのチケットに取り組み、ファイルを編集し、チェックを動かし、コミットする。push はせず、`gh` も使わない。
- ユーザーの設定では、Grok はどの操作も人に聞かずに承認する。指揮役は push と `gh` を止める `--deny` のルールを付けて Grok を起動し、Claude Code にも同じルールを付ける。
- レビュー役はそのチケットを実装していないエージェントである。`code-review` スキルで変更をレビューする。Codex はすべてのチケットをレビューし、Claude Code が実装したチケットは Grok もレビューする。
- すべてのプルリクエストは人がマージする。

### 並行作業

- 最初のチケットは 1 つだけで動かし、ループが初めから終わりまで動くことを確かめる。
- 2 つ目のチケットからは、同時に最大 2 つのチケットを動かす。1 つは Claude Code、もう 1 つは Grok で動かす。動かすのは、開いているブロッカーがないチケットだけである。
- Mac のマイクとスピーカーを使って声で話すテストは、2 つのチケットを動かしている間も 1 つずつ行う。
- チケットごとに、`main` へのプルリクエストを 1 つ作る。ほかのチケットに依存するチケットは、そのチケットのプルリクエストがマージされてから始める。

### ワークツリー

- `git gtr new` はリポジトリの隣の `kazokuai-worktrees/` にそれぞれのワークツリーを作る。作ったあとに、`.gtrconfig` にあるフックの `mise trust` と `codegraph init` を動かす。これらのフックは、人が `git gtr trust` で承認する。
- `herdr worktree open` で、ワークツリーを herdr のワークスペースとして開く。指揮役はそこのペインでエージェントを起動する。
- ワークツリーはそれぞれ、自分の codegraph のインデックスを持つ。codegraph は渡されたパスから上へ向かって `.codegraph/` を探す。ワークツリーはメインのリポジトリの外にある。`.codegraph/` はコミットしない。

### チェックと CI

- `mise run check` はアプリについて `dart format --set-exit-if-changed`、`flutter analyze`、`flutter test` を動かす。Go のコードを足す最初のチケットで、`gofmt`、`go vet`、`go test` も足す。
- GitHub Actions はプルリクエストごとと `main` への push ごとに、`mise run check` を動かす。
- ADR 0001 で決めたとおり、画像比較テストは作らない。

### 文章

- issue、仕様書、プルリクエストの本文、コミットメッセージ、ADR は日本語で書く。
- プルリクエストの本文と仕様書は、`yomiyasu` スキルで推敲する。チケットは、主な読み手が実装役なので推敲しない。
- ADR は英語で書き、plamo-translate で訳してから、`yomiyasu` スキルで推敲する。

## Consequences

### Pros

- どのエージェントも 1 つのコマンドで自分の作業を確かめられ、CI はプルリクエストごとに同じコマンドを動かす。
- 2 つのエージェントが互いのファイルに触れずに 2 つのチケットを同時に進められる。
- それぞれの変更を別のエージェントがレビューし、マージするかどうかは毎回、最後に人が決める。
- どのワークツリーにも最初から codegraph のインデックスがあるので、エージェントはそこでコードを検索できる。
- 似たチケットで Claude Code と Grok を比べ、`/retro` で役割を変えられる。

### Cons

- 人がすべてのプルリクエストをレビューしてマージしなければならない。並行して進めると、プルリクエストがたまる。
- `internal/protocol/` や `pubspec.yaml` のように同じファイルを変えるチケットどうしは、マージするときに競合する。
- Mac での声のテストは並行して動かせない。
- 3 種類のエージェントを使うので費用が増え、エージェントごとの設定を食い違わないように保つ必要がある。
- CI は、キャッシュが復元されないときは実行のたびに Flutter をインストールするので、時間がかかる。
- `.gtrconfig` のフックを変えるたびに、人がもう一度承認しなければならない。また、Claude Code と Grok が新しいワークツリーのフォルダーごとに、信頼するかどうかを聞いてくるかもしれない。
