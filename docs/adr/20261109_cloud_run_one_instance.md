# ADR 0011: Cloud Run を 1 インスタンスにし、つながっている電話機をメモリーで持つ

## Status

Accepted

## Context

ADR 0003 はバックエンドを Cloud Run で動かし、リージョンを asia-northeast1 にする。ラズパイへの指示は Firestore に書く。ラズパイとの WebSocket を持っている Cloud Run のインスタンスが指示を購読し、転送する。ADR 0003 は電話のあとの処理も Cloud Tasks で動かす。予約は Cloud Scheduler と Cloud Tasks で扱う。

バックエンドはつながっている電話機をメモリーに置く。Cloud Run の 2 つ目のインスタンスは、その電話機を見ない。指示が WebSocket を持っていないインスタンスに届くことがある。まとめは報告を受け付けた HTTP の応答のあとに作る。その応答を返したあとで Cloud Run が CPU を絞ると、まとめが止まる。

ハッカソンでは、この判断が ADR 0003 の 2 つを置き換える。1 つは Firestore を通した指示の中継で、もう 1 つは電話のあとの処理を Cloud Tasks で動かすことである。ADR 0003 の Status は Accepted のままである。リージョンを含むほかの判断はそのまま残る。予約と Cloud Scheduler と Cloud Tasks は ADR 0003 に書いたとおり残る。この判断はハッカソンのあとに見直す。

## Decision

- Cloud Run のインスタンスは最大 1 つで、最小は 0 である。
- サービス全体の上限も 1 である。リビジョンを切り替えているあいだも、インスタンスは 2 つにならない。
- インスタンスが生きているあいだ CPU を割り当て続ける。応答のあとのまとめは絞られない。
- リクエストの時間の上限は 3600 秒である。WebSocket はそのあいだ開いていられる。
- つながっている電話機はその 1 つのインスタンスのメモリーに置く。指示はインスタンスが購読するために Firestore へ書かない。
- 電話のあとのまとめはバックエンドのプロセスで作り、Cloud Tasks では作らない。
- ハッカソンのあと、ADR 0003 の Firestore の中継と Cloud Tasks に戻すかを見直す。そちらは、インスタンスを 1 つより多く動かせる。

## Consequences

### Pros

- 指示は電話機を持っているインスタンスに届く。
- CPU を割り当て続けるので、応答のあともまとめが続く。
- WebSocket は Cloud Run のリクエスト時間の上限まで開いていられる。
- ハッカソンの実装には指示のための Firestore の購読も、まとめのための Cloud Tasks のキューも要らない。

### Cons

- 上限は 1 インスタンスである。つながっている電話機は、すべてそれを使う。
- インスタンスが生きているあいだは、処理中のリクエストが無くても、CPU の料金がかかる。
- クラッシュや新しいリビジョンで、メモリーに置いた電話機は消える。電話機はつなぎ直す。ADR 0003 は、WebSocket が最長 60 分であることと、ラズパイがつなぎ直すことを、すでに書いている。
- Cloud Tasks と Cloud Scheduler は、予約とかけなおしのために ADR 0003 に残る。この判断ではそれらを作らない。予約とかけなおしを作るときに足す。
- インスタンスを 2 つ以上にするには、この判断が脇に置く Firestore の中継か、接続を共有する別の場所が要る。
